# MAX Account API Wiki

Документация **v1.0.0** для сервера **v1.11.0**, Python 3.10 и Docker. Сверена с исходным кодом проекта 27 сентября 2026 года. Wiki — отдельный сайт на порту 8088; Web GUI и HTTP API работают на 8087.

## 01 · Что это за API

Сервис подключает пользовательский аккаунт MAX через QR и предоставляет HTTP-доступ к сообщениям, чатам, истории, расписаниям и пересылкам. Внутри используется неофициальный клиент PyMax 2.4.1. Это не официальный Bot API MAX: отдельный bot token здесь не выдаётся, бот действует от имени подключённого аккаунта.

Есть три способа работы: Web GUI для ручного управления, Python-клиент для своего приложения, HTTP-запросы со стороннего сервиса. Они обращаются к одной базе аккаунта. Сохранение черновика, запуск рассылки и настройка правила доступны всеми этими способами.

| Понятие | Значение |
|---|---|
| API_KEY | Секрет вашего сервера. Админский задаётся в .env, пользовательский создаётся администратором |
| QR / сессия MAX | Вход в сам мессенджер; API-ключ его не заменяет |
| chat_id | ID чата MAX, иногда отрицательный; берётся из списка чатов |
| message.id | ID сообщения MAX; не равен update_id |
| update_id | Локальный порядковый номер события в базе вашего аккаунта |
| Сохранённое сообщение | Шаблон текста, фото, получателей и расписания |
| Запуск / run | Снимок шаблона и очередь доставок |
| Правило пересылки | Постоянное наблюдение за новыми событиями выбранных источников |

В 3D-схеме на главной можно выбирать узлы. Она показывает путь запроса: клиент → HTTPS → API → аккаунт MAX. Текст wiki работает и без WebGL. Ключи в эту wiki вводить не нужно.

## 02 · Установка и первый вход

Начиная с v1.10.1 основной Docker Compose запускает два сервиса: max-api
на порту 8087 и wiki на 8088. Отдельно запускать Python-сервер документации
не требуется. В корневом .env можно задать WIKI_BIND_HOST=0.0.0.0,
чтобы открыть документацию по http://IP_СЕРВЕРА:8088. По умолчанию доступ
локальный; используйте SSH-туннель или свою конфигурацию HTTPS proxy.
После изменения настройки выполните docker compose up -d --build --force-recreate wiki.
Контейнер документации не получает API_KEY и не имеет доступа к сессиям MAX.


Нужен архив сервера max-userbot-v1.11.0.zip, Docker с Compose v2 и Python 3 для генерации ключа. Команды ниже выполняются в терминале сервера.

```bash
unzip max-userbot-v1.11.0.zip
cd max-userbot
python3 setup.py
docker compose up -d --build
docker compose ps
curl http://127.0.0.1:8087/healthz
```

Ожидается `{"ok":true}`. Файл `.env` создаётся один раз; повторный setup.py не заменяет его. Найдите в нём значение API_KEY. Это админский ключ, а не ключ с сайта MAX. Не копируйте его в скриншоты, публичные репозитории и браузерные скрипты стороннего сайта.

При локальной установке откройте http://127.0.0.1:8087. Для сервера используйте SSH-туннель с вашего компьютера:

```bash
ssh -L 8087:127.0.0.1:8087 user@server
```

Пока туннель открыт, локальный адрес ведёт к серверу. Введите API_KEY в карточке доступа, нажмите «Подключить панель». Затем во вкладке подключения нажмите «Начать вход», отсканируйте QR приложением MAX на телефоне и подтвердите вход. Если запрошена 2FA, введите пароль. Дождитесь состояния connected.

Доступ к панели и подключение MAX — разные этапы. С ключом можно сохранять черновики при отключённом MAX, но отправлять сообщения и читать удалённую историю нельзя. После обновления страницы ключ вводится снова. Сессия MAX хранится в Docker volume и восстанавливается сервером.

Для доступа в доверенной локальной сети можно задать `BIND_HOST=0.0.0.0` в .env и выполнить `docker compose up -d --force-recreate`. В интернете используйте HTTPS, описанный ниже. По умолчанию порт слушает только localhost.

## 03 · Web GUI: все вкладки

С v1.10.4 при переключении вкладок обновляется адрес: #connect, #editor,
#saved, #favorites, #queue, #events, #relays, #logs, #admin.
Например, http://127.0.0.1:8087/#relays открывает пересылки после ввода ключа.
Работают «Назад/Вперёд» и восстановление вкладки после обновления страницы.
Ключ остаётся только в памяти браузера и после перезагрузки вводится заново.
Неизвестные вкладки и #admin без прав администратора переводят на #connect.
Ссылка не сохраняет несохранённый текст редактора и не выбирает чужой аккаунт.


### Оформление: Bootstrap, темы и день/ночь

С v1.11.0 панель использует локальный Bootstrap 5.3.8 без CDN.
Над вкладками доступны темы Ирис, Океан, Лес и Роза, каждая в дневном и ночном вариантах.
Режим «Авто» следует настройке системы, включая её изменение.
Выбор сохраняется в localStorage для адреса сервера, синхронизируется между
вкладками браузера и применяется к экрану входа. Ключ API туда не записывается.
При запрете localStorage тема действует до закрытия страницы.
После обновления выполните Ctrl+F5. Для обновления wiki замените папку wiki
и пересоберите её Docker-сервис.

### Подключение

Проверяйте состояние MAX, запускайте QR-вход и вводите 2FA. Остановка подключения не удаляет сохранённую сессию; после перезапуска сервера она может восстановиться. Это не отзыв сессии на стороне MAX.

### Редактор сообщения

1. Создайте новое сообщение, загрузите все чаты.
2. Выберите получателей галочками. Поиск не сбрасывает уже выбранные чаты. «Выбрать показанные» выбирает текущий отфильтрованный список.
3. Укажите внутреннее название, текст и при необходимости одно фото.
4. Установите фиксированную паузу 5–30 секунд между попытками отправки в рамках запуска.
5. Нажмите «Сохранить» для черновика или «Сохранить и отправить сейчас» для постановки в очередь.

Черновик без получателей можно сохранить при выключенном расписании. Отправка и активный cron требуют хотя бы одного получателя. Пустой текст разрешён только вместе с фото. Лимиты: 4000 символов, 1000 уникальных получателей, одна картинка JPEG/PNG/WebP до 10 МиБ и 20 мегапикселей.

### Сохранённые сообщения

Здесь общий список, поиск, расписания и ближайшее время запуска. «Открыть» переносит настройки в редактор; сохранение применяет изменения. «Удалить» удаляет шаблон и отменяет ещё не начавшиеся доставки этого шаблона. Уже созданные запуски содержат снимок: изменение текста не меняет их содержимое.

### Расписание мышкой

Выберите периодичность, дни недели или день месяца, часы и минуты. Установите флажок включения cron. «Ближайшие запуски» помогает проверить результат. По умолчанию выбран **Анадырь · Asia/Anadyr (UTC+12)**. Старые сохранённые расписания сохраняют прежний часовой пояс. Расписание исполняет сервер; браузер можно закрыть.

### Избранные

Нажмите звёздочку у чата в редакторе. На вкладке избранного можно создать сообщение для выбранного набора. Удаление из избранного не меняет получателей уже сохранённых сообщений.

### Очередь и результаты

Проверяйте каждую доставку. Принятие задания не равно отправке, отправка не равна прочтению. Отмена касается ожидающих доставок: начавшаяся может закончиться. При состоянии unknown сначала проверьте чат вручную. После сбоя сервер не повторяет такую отправку автоматически.

### Входящие

Выберите чат слева, сообщения появятся справа. При подключённом MAX читается его история, включая сообщения до установки сервиса; при отключённом — только локально накопленные события. Кнопка загрузки предыдущих сообщений читает следующую страницу истории.

Стили и фото отображаются по данным MAX. Неизвестные стили становятся обычным текстом; видео и опросы не воспроизводятся. «Импортировать в сообщение» переносит текст, эмодзи и первую фотографию в новый черновик, без получателей и активного cron. Нативное оформление в обычный редактор не переносится. Импорт не отправляет сообщение. При нескольких фото редактор берёт первое; автоматическая копия поддерживает до десяти.

### Пересылки

Укажите название, режим, получателя и исходные чаты. У назначения есть поиск и фильтры «Группы / Каналы / Личные»; выбранный получатель сохраняется при фильтрации. Под источниками видны их количество и названия.

- **Переслать**: обычный forward средствами MAX.
- **Создать новое**: копия текста, нативного оформления и фото. Можно отключить подпись или добавить гиперссылку с названием исходного чата. Цель ссылки — чат либо конкретное исходное сообщение.

Включите правило после сохранения. Оно обрабатывает новые события, полученные после включения, без перечитывания прежней истории. История за простой не догружается автоматически. Пауза 5–30 секунд применяется в рамках правила, а не как общий лимит всех отправок аккаунта.

Перепосты с признаком FORWARD пропускаются в обоих режимах; обычные ответы REPLY допускаются. Дубли текста и одинаковых байтов фото в одно назначение подавляются даже между разными правилами одного аккаунта. Это не поиск смысловых дублей: изменённый текст и перекодированное фото могут пройти. Если две копии не имеют признака перепоста, отправляется первая полученная; первоначального автора сервис по ним не определит. Для других вложений штатного forward используются доступные ID медиа; без них фильтр ограничен ID исходного сообщения.

Ссылки используют max.ru; открытие приложения зависит от устройства. Закрытые чаты доступны участникам. Копирование видео и других неподдерживаемых вложений завершается ошибкой целиком; используйте обычную пересылку. Циклы правил и источник, совпадающий с назначением, запрещены.

Выключение отменяет ожидающую очередь. Повторное включение берёт только новые события. Смена источников/назначения тоже сбрасывает ожидающие задания. Режим и параметры ссылки уже поставленных заданий сохраняются до завершения. «Последние отправки» загружаются только кнопкой, по 100 записей.

### Администратор

Админский ключ из .env открывает вкладку пользователей. Создайте пользователя и сохраните показанный ключ: повторно его получить нельзя. Пользователь подключает свой MAX; его чаты, события, шаблоны и пересылки изолированы.

Доступны переименование, замена ключа, блокировка, разблокировка, удаление и открытие панели аккаунта. Замена ключа отзывает старый. Блокировка прекращает доступ и фоновые задачи; после разблокировки сохранённые задачи могут продолжиться. Удалённые данные перемещаются в `/data/deleted`, автоматической панели восстановления нет.

Статистика показывает накопленные сервисом события, сохранённые сообщения, расписания, правила, доставки, API-запросы, ошибки, размер файлов и время работы. Это не полная статистика MAX и не подтверждения прочтения. Сводка по запросам ведётся по UTC; журнал хранит последние административные действия. Администратор может управлять аккаунтом через X-User-ID, обычному пользователю этот заголовок запрещён.

## 04 · Договор HTTP API

Базовый адрес примеров: `https://max-api.example.com` без `/api` на конце. Замените домен и ID собственными. Запросы `/api/*` требуют заголовок:

```http
Authorization: Bearer YOUR_USER_API_KEY
```

У запроса JSON добавьте Content-Type: application/json. Для multipart boundary формирует HTTP-клиент: не устанавливайте application/json вручную. Ключ не передаётся в URL. Все обычные пользовательские операции доступны и администратору. Для чужого аккаунта администратор добавляет `X-User-ID: USER_ID`.

ID чатов и сообщений храните строками. API принимает числовые строки в полях int; ответ сериализует ключевые MAX ID строками, чтобы JavaScript не округлял 64-битные значения. Не преобразуйте их через Number в n8n или другом JS-коде. update_id — отдельный локальный счётчик.

| Курсор | Где используется | Единицы / порядок |
|---|---|---|
| next_marker → marker | /chats | Непрозрачный серверный маркер, передавайте как есть |
| next_offset → after | /updates | Локальный update_id; выдача по возрастанию |
| next_before → before | /history/{chat_id} | Время MAX в миллисекундах, старые сообщения |
| next_before → before | /inbox/{chat_id} | Локальный update_id, старые события |
| upcoming | /schedule/preview | Unix timestamp в секундах |

`/healthz` сообщает, что процесс отвечает, а не что MAX подключён. Это проверяет `/api/status`. OpenAPI tenant-сервиса доступна по `/openapi.json`; админские маршруты шлюза туда не включены. В wiki приложены обе схемы отдельно. `/docs` и `/redoc` в сервере выключены.

Запросы на отправку не имеют ключа идемпотентности. При сетевом обрыве/HTTP 502/504 доставка может состояться. Автоматический повтор POST способен создать дубль. Проверяйте историю вручную. Приём задания со статусом 202 означает очередь, а не успешную доставку.

## 05 · Python: подключение и QR

В папке examples находится client.py, использующий стандартную библиотеку Python 3.10. Устанавливать requests не нужно. Скопируйте examples в отдельный рабочий каталог вне опубликованной wiki и запускайте примеры там. Не сохраняйте ключи, QR, логи и файлы сессий в каталоге сайта. Переменные примеров не являются переменными Docker сервера:

```bash
export MAX_API_URL='http://127.0.0.1:8087'
read -r -s -p 'Пользовательский API-ключ: ' MAX_API_KEY
export MAX_API_KEY
python3 client.py
```

Для внешнего сервера задайте HTTPS-адрес. Команда client.py выводит статус и все страницы списка чатов. При отключённом MAX список вернёт 409; сначала авторизуйтесь через GUI либо код ниже.

```python
from pathlib import Path
import time
from client import MaxAPI

api = MaxAPI()
api.request('POST', 'auth/start')
for _ in range(90):
    status = api.request('GET', 'status')
    print(status['state'])
    if status['state'] == 'connected':
        break
    if status['qr_available']:
        Path('qr.png').write_bytes(api.request('GET', 'auth/qr', binary=True))
        # Откройте qr.png и подтвердите вход на телефоне.
    if status['state'] == 'password_required':
        from getpass import getpass
        api.request('POST', 'auth/password', {'password': getpass('2FA: ')})
    time.sleep(2)
else:
    raise RuntimeError('Вход не завершён; проверьте status и запустите снова')
```

QR может обновляться; сохраняйте актуальный файл. Состояния входа определяет `/status`; не отправляйте пароль, пока он не запрошен. Не публикуйте QR и файл сессии.

## 06 · Python: текст, фото и история

Примеры ниже выполняют реальные отправки. Сначала выберите тестовый чат, доступный вашему аккаунту.

```python
from client import MaxAPI
api = MaxAPI()
chat_id = '-123456789'  # Заменить значением из api.chats()
result = api.send(chat_id, '**Привет!** 👋\n_Сообщение из Python_')
print(result)
api.photo(chat_id, 'image.jpg', '**Фото** 📷')
# Ответ на конкретное сообщение:
# api.send(chat_id, 'Принято', reply_to='MESSAGE_ID')
```

| Оформление | Синтаксис в text |
|---|---|
| Жирный | `**текст**` |
| Курсив | `_текст_` |
| Подчёркивание | `__текст__` |
| Зачёркивание | `~~текст~~` |
| Код | Одинарные обратные кавычки |
| Гиперссылка | `[название](https://example.com)` |
| Цитата | `> текст` в начале строки |
| Заголовок | `# текст` в начале строки |

Это ограниченный Markdown PyMax, не HTML. Inline-стили не переходят через перенос строки; экранирование обратным слешем не поддерживается. Эмодзи передаются Unicode. У сообщений в истории оформление хранится отдельно в elements с UTF-16-смещениями.

```python
before = 0
for _ in range(3):  # Не более трёх страниц для примера
    page = api.request('GET', f'history/{chat_id}', params={'before': before, 'limit': 50})
    for item in page['messages']:
        message = item['message']
        print(message['id'], message.get('sender'), message.get('text'))
    before = page['next_before']
    if before is None:
        break
```

История запрашивается у MAX и требует соединения. `/updates` читает только локальный журнал и не заменяет архивную историю. В нём могут быть и сообщения вашего аккаунта. Повторное событие с теми же chat_id и message.id не добавляется; изменения сообщения не образуют полноценный поток правок.

## 07 · Python: шаблоны, cron и пересылки

Создание/изменение сохранённого сообщения — **форма с полем payload, содержащим JSON**, а не обычный JSON POST.

```python
import json
from client import MaxAPI
api = MaxAPI()
payload = {
    'title': 'Утреннее сообщение',
    'text': '**Доброе утро!** ☀️',
    'chat_ids': ['-123456789', '987654321'],
    'interval_seconds': 10,
    'cron': '0 9 * * 1-5',
    'timezone': 'Asia/Anadyr',
    'enabled': False,
    'notify': True
}
draft = api.save(payload)
identifier = draft['id']
print(api.request('POST', 'schedule/preview', {
    'cron': payload['cron'], 'timezone': payload['timezone']
}))
# Включение расписания после проверки:
# api.request('PATCH', f'saved-messages/{identifier}/schedule', {'enabled': True})
# Разовый запуск:
# run = api.request('POST', f'saved-messages/{identifier}/send')
# print(api.request('GET', 'send-runs'))
# api.request('POST', f"send-runs/{run['id']}/cancel")
# Изменение передаёт полный payload:
payload['text'] = 'Обновлённый текст'
api.save(payload, identifier=identifier)
# Фото: api.save({**payload, 'photo_action': 'replace'}, 'image.jpg', identifier)
# Удалить фото: api.save({**payload, 'photo_action': 'remove'}, identifier=identifier)
# Удалить шаблон: api.request('DELETE', f'saved-messages/{identifier}')
```

Cron содержит пять полей: минута, час, день месяца, месяц, день недели. `0 9 * * 1-5` — будни в 09:00 выбранного часового пояса. Не добавляйте поле секунд. Preview возвращает пять времён в Unix-секундах. Для печати используйте datetime.fromtimestamp(value, ZoneInfo('Asia/Anadyr')).

Новые события для автоматического правила:

```python
rule = api.request('POST', 'relays', {
    'title': 'Новости в канал',
    'destination': '-300',
    'source_chat_ids': ['-100', '-200'],
    'interval': 5,
    'enabled': False,
    'mode': 'copy',
    'add_source': True,
    'link_target': 'message'
})
# Замените ID выше реальными; затем можно включить:
# api.request('PATCH', f"relays/{rule['id']}/enabled", {'enabled': True})
# Обычная пересылка: mode='forward'; add_source/link_target в ней игнорируются.
print(api.request('GET', 'relays'))
print(api.request('GET', 'relays', params={'include_jobs': 'true', 'limit': 100}))
```

Правило принимает до 100 уникальных источников. PUT /relays/{id} передаёт весь объект, PATCH .../enabled меняет только включение. Значения mode: copy/forward; link_target: chat/message. У новых правил ссылка по умолчанию ведёт на чат, старые правила сохраняют прежний режим ссылки на сообщение.

## 08 · Доступ со стороннего сервиса через интернет

Нужны домен, сервер с публичным IP и входящие TCP-порты 80/443. Создайте DNS A-запись max-api.example.com на IP сервера. Если есть AAAA, IPv6 тоже должен вести на доступный сервер. За NAT потребуется проброс портов. Порт 8087 оставьте на 127.0.0.1.

В комплекте deploy есть дополнительный Compose-файл и Caddyfile. Скопируйте их в **существующую папку API**, рядом с его compose.yaml. Замените домен в Caddyfile. Caddy присоединится к той же Docker-сети и направит запросы на max-api:8087.

```bash
# Выполнять из прежней папки max-userbot:
docker compose -f compose.yaml -f compose.https.yaml up -d --build
docker compose -f compose.yaml -f compose.https.yaml logs --tail=50 caddy
curl https://max-api.example.com/healthz
```

Для последующих команд этой установки используйте ту же пару `-f`. Caddy получает сертификат и перенаправляет HTTP на HTTPS при корректном DNS и доступных портах. Не запускайте второй proxy на уже занятых 80/443: добавьте маршрут в существующий. Для nginx альтернативно нужны TLS-настройки и лимит тела не меньше 12m для фото. Полные TLS-инструкции: официальные ссылки в конце wiki.

Настройка HTTP-модуля любого внешнего сервиса:

| Поле | Значение |
|---|---|
| Method | POST |
| URL | https://max-api.example.com/api/messages |
| Authentication / header | Authorization: Bearer пользовательский_ключ |
| Content-Type | application/json |
| Body | JSON ниже |
| Timeout | Не менее 150 секунд для операций с фото |
| Automatic retry | Выключен для отправки |

```json
{
  "chat_id": "-123456789",
  "text": "**Новый заказ** 📦\nНомер: 12345",
  "notify": true
}
```

В n8n это узел HTTP Request, в Make — HTTP-модуль: названия полей могут отличаться по версии. Секрет сохраните в хранилище credentials сервиса. Сначала выполните GET /api/status, затем один POST в тестовый чат. Для фото используйте multipart: chat_id, text и бинарное поле photo; URL картинки не заменяет загрузку файла. Для шаблона используйте строковое поле payload с JSON и при необходимости бинарный photo.

Если внешняя система повторяет одно бизнес-событие, ведите у неё таблицу обработанных order_id/event_id. Фильтр дублей пересылок не защищает обычный POST /messages. Автоматический повтор после таймаута отключите, результат проверьте отдельно.

Входящие для внешнего сервиса организуются опросом: по таймеру GET /api/updates?after=OFFSET&limit=100, обработка массива updates, сохранение next_offset. Сохраняйте позицию в постоянном хранилище, не в памяти одного выполнения. Не запускайте конкурентные обработчики одного курсора. Встроенной регистрации webhook, callback URL и long polling в этой версии нет.

Клиентский JavaScript публичного сайта не должен содержать ключ: используйте свой backend. CORS для сторонних браузерных origins в сервере не включён. Серверные HTTP-запросы из Python/CRM/автоматизации CORS не затрагивает. Внешнему сервису давайте пользовательский ключ: он всё равно имеет полный доступ к своему аккаунту, ключей только для отправки пока нет.

## 09 · Пример бота команд

Готовый examples/bot.py отвечает на `/help`, `/ping`, `/time`. Он работает через этот HTTP API и пишет от имени пользовательского аккаунта. Для первого запуска используйте отдельный тестовый аккаунт или чат.

1. В админ-панели создайте пользователя для интеграции. Войдите его ключом и подключите MAX через QR.
2. Получите ID тестового чата командой python3 client.py.
3. Отправьте в этот чат со своего подключённого аккаунта уникальный текст, например `определить-id-бота-001`.
4. Прочитайте /api/history/{chat_id}; найдите это сообщение и возьмите поле sender. Это BOT_OWN_ID. Endpoint для собственного профиля в данной версии отсутствует.
5. Скопируйте examples в отдельный каталог вне сайта wiki. Там скопируйте bot.env.example в bot.env, заполните MAX_API_URL, MAX_API_KEY, BOT_OWN_ID и BOT_CHAT_IDS. Несколько ID чатов разделяются запятыми.
6. Запустите Docker-пример ниже. С другого аккаунта отправьте /ping в разрешённый чат: ожидается pong 👋.

```bash
cp -R examples "$HOME/max-command-bot"
cd "$HOME/max-command-bot"
cp bot.env.example bot.env
# Отредактируйте bot.env: замените все примерные значения.
chmod 600 bot.env
docker compose up -d --build
docker compose logs -f bot
```

Это отдельный Compose-проект бота. Из контейнера `127.0.0.1:8087` указывает на сам контейнер бота, а не на API; используйте HTTPS-домен. При запуске Python на том же хосте можно использовать локальный API:

```bash
# После заполнения bot.env. Формат примера совместим с bash:
set -a
. ./bot.env
set +a
python3 bot.py
```

На Linux нужен установленный пакет часовых поясов tzdata; на Windows при отсутствии IANA-базы выполните `python -m pip install tzdata`. В Docker-примере системная база устанавливается автоматически.

Бот игнорирует собственный sender, неподтверждённый sender, перепосты и чаты вне разрешённого списка. Он отвечает только на точные команды, а не на любой текст, чтобы избежать циклов с другими ботами. BOT_OWN_ID должен соответствовать подключённому аккаунту, иначе собственные сообщения могут ошибочно обрабатываться.

При первом запуске бот проходит существующий локальный журнал без ответов и сохраняет текущую позицию. Команды, пришедшие во время этого начального прохода, тоже могут быть пропущены; отправьте тест после сообщения в логе о готовности. После перезапуска бот продолжает с сохранённого курсора и обрабатывает накопленные события.

Перед отправкой бот записывает попытку в SQLite. Если процесс падает или HTTP-результат неизвестен, попытка не повторяется автоматически. Это выбор в пользу отсутствия повторных ответов ценой возможного пропуска; гарантия exactly-once не заявляется. Смотрите attempts в bot-state.sqlite или /state/bot.sqlite контейнера. Запускайте один экземпляр на одну базу; разные копии с отдельными базами могут ответить повторно. Не удаляйте volume bot-state при обновлении.

Чтобы добавить команду, измените reply_for в bot.py: верните строку ответа для нужного текста или None для пропуска. При подстановке произвольного пользовательского текста учитывайте Markdown. Пример специально отвечает фиксированным текстом и не выполняет команды из сообщений.

## 10 · Справочник маршрутов

Во всех таблицах пути начинаются с /api, если явно не указано другое. Требуется Bearer-ключ. Полные поля запросов, типы и ответы в разделах OpenAPI ниже; модели возвращаемых MAX сообщений зависят от клиента, поэтому произвольные дополнительные поля не считаются стабильным контрактом.

### Подключение и чаты

| Метод | Путь | Тело / параметры | Результат |
|---|---|---|---|
| GET | /status | — | state, error, password_hint, qr_available |
| POST | /auth/start | — | Запуск/восстановление подключения, статус |
| POST | /auth/stop | — | Остановка с запретом автозапуска, статус |
| POST | /auth/logout | — | Выход из MAX, session_removed и remote_revoked |
| GET | /auth/qr | — | PNG; 409, если QR не готов |
| POST | /auth/password | JSON password (1–1024) | accepted |
| GET | /chats | marker ≥ 1; cached=false | chats, next_marker, complete, warning |

## 11 · Ошибки и диагностика

### Ошибка proto.payload при обычной пересылке

В v1.10.3 исправлен тип link.messageId: нативный запрос пересылки отправляет
целочисленный ID вместо строки из модели PyMax 2.4.1. Точность ID проверена
сериализатором WebSocket. Это устранение обнаруженного расхождения с запросом
веб-клиента; успешная доставка должна быть подтверждена на вашем аккаунте.
Для проверки создайте новое оригинальное сообщение с уникальным текстом.
Старые unknown-задания не повторяются и отпечатки не очищаются автоматически.
Если MAX снова отклонит запрос, сохраните свежий журнал с max_error_code.

### Вкладка «Логи» (начиная с API v1.10.0)

Откройте «Логи» и нажмите «Обновить» после воспроизведения ошибки. Выберите ERROR для ошибок, WARNING для отклонённых запросов или все уровни. «Предыдущие записи» загружает более старые записи. «Скачать показанные JSON» сохраняет только уже загруженный список с выбранным фильтром.

Журнал отдельный у каждого аккаунта. Администратор открывает панель нужного пользователя и переходит в его «Логи». Ошибки входа без действующего ключа и операции администрирования записываются в журнал администратора. Ключи, тела запросов, query string, пароли, QR и тексты переписок не записываются. У исключения сохраняются класс и последние места в коде (файл, функция, строка), без текста исключения и локальных переменных.

В v1.10.2 записи ApiError содержат max_error_code и max_opcode, когда MAX передал структурированный код. Свободный текст ответа и payload не записываются. Для пересылки operation показывает copy или forward. Если журнал старой версии содержит только ApiError, точную причину задним числом восстановить нельзя: нужна новая попытка с новым оригинальным сообщением. Старые unknown-задания автоматически не повторяются.

Все HTTP-ответы получают заголовок X-Request-ID. При ошибке панель показывает «Запрос: …». Найдите этот request_id в скачанном JSON: он связывает запрос и синхронную внутреннюю ошибку. Фоновые отправки связываются по run_id либо rule_id/job_id. Успешные GET-опросы не засоряют журнал; записываются изменения, ошибки, вход MAX и результаты отправок. Старые ошибки, возникшие до обновления, восстановить нельзя — воспроизведите проблему снова.

GET **/api/logs**: параметры level=INFO/WARNING/ERROR (необязательный), before=0, limit=100 (1–500). Ответ: logs, next_before, retention=5000, timezone=UTC. Передавайте next_before как before для следующей страницы. На сервере хранятся последние 5000 записей в diagnostics.sqlite каждого аккаунта; панель показывает время в Asia/Anadyr, JSON — ISO UTC. Записи также выводятся в stdout контейнера. Compose новой версии ограничивает Docker-лог тремя файлами по 10 МиБ. На старой установке перенесите секцию logging из нового compose.yaml, сохраняя прочие собственные настройки.

```bash
curl -H "Authorization: Bearer $MAX_API_KEY" \
  "$MAX_API_URL/api/logs?level=ERROR&limit=100" > max-errors.json
docker compose logs --since=30m --tail=200 max-api
```

Логи API, proxy и бота — разные журналы. Если запрос не дошёл до API (ошибка DNS, TLS, 502 от proxy), смотрите docker compose logs caddy. Docker Engine может отдельно сообщать о старте контейнера и ошибках запуска. В логах нет полного содержимого переписки: для отчёта достаточно версии, действия, времени, request_id и соответствующих записей.


| Симптом / код | Проверка и действие |
|---|---|
| IP:8087 недоступен | По умолчанию bind=127.0.0.1; используйте SSH или HTTPS proxy. Проверьте compose ps и firewall |
| 401 | Bearer-ключ неверен, заменён, пользователь удалён/заблокирован; проверьте /whoami |
| 403 | Пользователь вызвал /admin или передал X-User-ID |
| 404 | Неверный маршрут/ID или у шаблона нет фото |
| 409 | Часто MAX отключён, QR/2FA не готов; читайте detail и /status |
| 422 | Ошибка JSON/формы, лимитов, cron, самопересылка или цикл правил |
| 413 / фото не проходит | Ограничение proxy либо файл превышает допустимый размер |
| 502 / 504 на отправке | Результат может быть неизвестен: не повторять автоматически |
| 500 | Сохраните метод, маршрут, время и обезличенную ошибку; изучите лог контейнера |
| Чатов мало | Пройдите все next_marker, не используйте cached=true; проверьте complete и warning |
| Бот молчит | connected, верные BOT_OWN_ID/BOT_CHAT_IDS, точная команда, другой sender, первый проход уже завершён |
| Cron молчит | enabled, получатели, часовой пояс, preview, соединение MAX, scheduler_error |
| Пересылка пропущена | FORWARD/дубль, событие раньше включения, правило выключено или недоступные вложения |
| Не открывается приложение по ссылке | Настройки устройства/браузера; доступ участника к закрытому чату; проверка ссылки на телефоне |

```bash
docker compose ps
docker compose logs --tail=100 max-api
curl -H "Authorization: Bearer $MAX_API_KEY" "$MAX_API_URL/api/status"
```

Тело ошибки обычно содержит detail (строка либо массив ошибок валидации). Не отправляйте для диагностики .env, QR, содержимое сессии, пользовательские ключи и полные личные переписки.

## 12 · Обновление и резервная копия

Обновляйте в прежней папке Compose, чтобы сохранить имя проекта и его volume. Заменяйте app и requirements.txt из новой версии, сохраняйте .env, compose.yaml и volume. Затем docker compose up -d --build --force-recreate, после — Ctrl+F5. Если подключён HTTPS, используйте оба Compose-файла. Не выполняйте down -v: удалятся данные.

Для согласованной копии SQLite сначала остановите API. Пример выполняется из корня проекта API, копирует весь /data и .env в закрытую папку backup. Храните её отдельно от публичного веб-каталога.

```bash
mkdir -p backup
chmod 700 backup
docker compose stop max-api
docker compose cp max-api:/data backup/data
cp .env backup/server.env
chmod -R go-rwx backup
docker compose start max-api
```

Если backup/data уже существует, выберите новый каталог с датой, чтобы не смешивать копии. Сохраните также compose.yaml, дополнительный compose.https.yaml и Caddyfile, если используются. Копия содержит доступ к сессиям MAX и требует такого же ограничения доступа, как ключи.

Восстановление делайте при остановленном API в volume того же проекта, предварительно сохранив текущее содержимое. Пример для замены всей базы на выбранную копию:

```bash
docker compose stop max-api
# Сначала отдельная копия текущего состояния; каталог должен быть новым:
docker compose cp max-api:/data backup/before-restore
# Копия должна содержать events.sqlite, campaigns.sqlite, relays.sqlite,
# users.sqlite и сессии/каталоги пользователей из одного момента времени.
docker compose cp backup/data/. max-api:/data/
docker compose start max-api
```

Копирование поверх не удаляет файлы, отсутствующие в архиве. Для строгого восстановления полного снимка используйте чистый volume с прежним набором данных и конфигурацией, а не смешивайте разные даты. После восстановления проверьте /whoami, соединение и очереди перед включением автоматизаций. Резервная копия бота делается отдельно из bot-state при остановленном боте.

Один процесс API на volume: не увеличивайте workers и не запускайте несколько экземпляров на одних SQLite-файлах. Публичный endpoint не имеет встроенных квот/rate limit; их можно задать на proxy. Ключ пользователя даёт доступ ко всем функциям его аккаунта, scopes не реализованы.

## Вход и завершение сессии в v1.11.1

MAX может временно отвечать `service.unavailable` на вход (opcode 19).
API теперь повторяет вход через 5, 10, 20 и 40 секунд с новым клиентом и прежней
сохранённой сессией. Во время ожидания статус `reconnecting`; после пяти неудачных
попыток — `error`. Это обработка временной недоступности MAX, а не гарантия
доступности внешнего сервера. Ошибки авторизации и отправки сообщений не повторяются.

- `POST /api/auth/stop` — отключить, сохранив сессию. Остановка сохраняется после
  перезапуска API; `POST /api/auth/start` явно возобновляет вход.
- `POST /api/auth/logout` — завершить текущую сессию MAX и удалить её локальную
  базу; история, настройки и другие пользователи сохраняются. В панели это
  кнопка «Завершить сессию MAX».
- При подключении logout вызывает отзыв текущего устройства через MAX. Если
  MAX ответил ошибкой, API возвращает 502/504 и сохраняет сессию для повторной попытки.
  Без подключения удаляется только локальная сессия: ответ `remote_revoked: false`;
  устройство следует завершить в приложении MAX. Новый вход требует QR.

Оба маршрута требуют `Authorization: Bearer <API_KEY>`; администратор может выбрать
пользователя заголовком `X-User-ID`. `logout` возвращает статус, `session_removed`
и `remote_revoked`. Он не завершает другие устройства аккаунта.

## Исправления API v1.11.2

Исправлена совместимость загрузки фото с URL без `photoIds`. PyMax 2.4.1
отказывался загружать такой файл до HTTP-запроса. Адаптер получает токен из
ответа загрузки: по указанному ID либо по единственному фото в ответе. Пустой,
неоднозначный ответ или несовпадение ID завершаются ошибкой без отправки сообщения.
Адаптер применяется также после переподключения клиента.

При ошибке загрузки журнал содержит безопасный `upload_stage`, без URL и токенов.
Такая доставка отмечается `failed` («Не отправлено»), а не `unknown`. Автоматического
повтора отправок нет; прежние `unknown`-задания не изменяются.

`not.found` на opcode 64 означает отказ MAX: сообщение или чат не найдены либо
недоступны. Проверьте исходное сообщение, чат назначения и доступ подключённого
аккаунта. Это не ошибка соединения; пересылка не заменяется копией и не повторяется.
Реальную загрузку на MAX нужно проверить после обновления с подключённым аккаунтом.
